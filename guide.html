A tool that fixes access-control bugs,
and proves it broke nothing.

Short version of the whole project. Read it top to bottom once and you can explain it to anyone.

1 · What are we actually building?In one minute, no jargon

The problem. A document portal (think: salary slips, contracts, KYC) lets people log in and open files. Developers check “are you logged in?” but forget “is this file yours?”. So Bob changes /documents/1 to /documents/2 and reads Alice's salary slip. That is the bug (IDOR / broken access control, #1 on the OWASP Top 10).
What you give Gatewise
  • the portal's URL (staging)
  • 2–4 test logins (Alice, Bob, Admin)
  • the app's code (git repo)
What you get back
  • Proof the leak is real (fake secret found where it shouldn't be)
  • a tiny patch (often 2–3 lines)
  • a permanent test + one-page certificate that nothing else broke
Analogy. A security guard who (1) walks to every door and shows which ones open for the wrong person, (2) fixes the lock with the smallest possible change, then (3) tries every door again to prove nobody who should get in was locked out.

Our three real differences

  1. We learn “who should see what” from the app itself. Each test user's own “My Documents / Shared with me / Team” pages are the answer key. No hand-written rules.
  2. A plain-code checker, not the AI, accepts the fix. It rebuilds the full who-can-open-what table before and after. Only the broken cells may change. The obvious “only the owner may open it” patch gets rejected because it locks out the person a file was shared with.
  3. The exploit becomes a permanent test. It runs in CI, so the next developer who forgets a check on a new endpoint gets caught automatically. That recurring protection is the real-world value.
Who needs this? Small and mid-size teams (fintech, HR, edtech) that hold personal documents, get a pentest or bug report with “IDOR on /documents”, and then sit on it because nobody can safely fix it quickly. Under India's DPDP Act 2023 (penalties up to ₹250 crore) that backlog is a liability.

3 · The sandbox question“We sandbox first, then exploit the URL, right?”

Almost, with one important refinement: we never experiment on the real site. Two lanes keep it safe.

Observe lane talks to the URL

Logs in as each test user and only reads (GET requests). Fake-secret proof only. Refuses any host not on the allowlist the owner signed off.

Verify lane talks to a copy

Every patch is tried on a local replica of the app built from its repo with fake data, in a network with no internet. The live site is never modified.

ModeTargetUsed for
A · LabOur own deliberately vulnerable portal, all fake data, all localHackathon demo and honest benchmarks (we know the right answers, so we can measure)
B · Your stagingURL + test logins + repo supplied by the owner, who confirms “I own this”The real use case. v1 auto-patches Python/FastAPI repos that boot locally; others get the proof + report only
Why the lab alone is not enough: judges will ask “is this a toy?”. Answer: Mode B is the product, the lab is the proving ground. Stretch goal: run the same engine on a second, differently written app to show it is not hard-wired to our portal.

4 · ArchitectureThe diagram you can redraw on a whiteboard

Solid arrows = data flow. Dashed = optional shortcut. Red dashed = the retry loop: the checker sends the exact cells it broke back to the AI. Amber = the only place AI is used.

The 8 steps with Alice and Bob

  1. Guard. Is staging.acme.test on the allowlist and did the owner confirm? If not, stop.
  2. Map. Log in as Alice: her “My Documents” shows files 1, 2, 4. Bob sees 3, plus 2 (shared with him). That is the answer key: Bob may open 2 and 3, never 1.
  3. Attack. Bob requests file 1. If the server answers, that cell of the table is a LEAK (expected “no”, got “yes”).
  4. Prove. File 1 secretly contains CANARY-d1-8f3a…. Seeing it in Bob's response (or an identical hash) is undeniable. A bare “200 OK” never counts. We auto-write a test that fails today.
  5. Locate. Python's ast finds the function that fetches the document without calling the existing can_access() helper. Other functions doing the same are sibling variants (/preview, /download…).
  6. Propose. The local AI drafts up to 5 tiny patches under rules: only that file, ≤20 lines, reuse can_access(), never touch tests.
  7. Check. On the replica, per patch: the failing test now passes; the whole table is recomputed and only the leak cells changed; recorded normal traffic replays identically; deliberately broken “mutant” fixes are caught. The smallest patch that passes wins.
  8. Deliver. Patch + permanent test + certificate; a person approves the PR. Never auto-merged.

8 · Things that can bite usAnd the cheap fix for each




RiskFix


Responses contain changing bits (timestamps, CSRF tokens, ETags), so “same response” looks different and we invent false collateralCompare status + normalised JSON (strip volatile keys, sort keys and lists); record each normal request twice and drop fields that change on their own; never hash raw HTML


The answer key (list screens) misses shared links, team access, paging, and a leaky list would mark the leak as “expected”Lab: the seed file is the answer key. Real apps: list screens only propose a small policy file; a human confirms it, and we flag only cells where policy and screens agree


Replica behaves differently from stagingRun the exploit test on the replica before patching and require it to fail. If it passes, the replica does not reproduce the bug: report “unverified” and stop


7B model writes junkStrict diff-only format, line cap, 5 tries, cached replay for the demo


“It only works on your toy”Be honest on scope; show the second app if time allows




Honest limit (say it out loud): the checker proves the bug is fixed for the table we tested. It does not prove no other bugs exist.




9 · Explain it in 60 secondsRead this to a friend


“Portals that store documents often check that you're logged in but forget to check the file is yours. We built Gatewise: you give it a staging URL, a few test logins and the code. It logs in as each user, works out who should see what from the app's own screens, then tries to open everyone else's files. If it gets one, it proves it with a hidden fake secret and writes a failing test. Then a small local AI proposes tiny patches, and a plain-code checker, not the AI, tries each on a copy of the app, re-tests every user and every file, and accepts only a patch that fixes the leak and changes nothing else. The obvious ‘owner only’ fix gets rejected because it locks out people a file was legitimately shared with. You end up with a verified patch, a permanent test, and a certificate a human can approve in minutes.”
